# Mi 6 APFS 根卷与 launchd 启动验证

本轮继续使用设备上的 `ios-apfs` 容器（XID 2）和 System/Data UUID，
通过 EDK2 Fastboot 临时运行 EFI 桥；没有重新生成大文件系统镜像。

## 根卷挂载的阻塞原因

`handoff-34` 至 `handoff-36` 中，`APFS_INODES` 创建正常，但挂载时
`z_pcpu_cache` 从零变成 `0x1000`。分配前后的哨兵表明，这次写入发生在返回
APFS 之后。`handoff-37` 的诊断陷阱进一步确认 4 KiB 分配缓冲区及全局计数器
地址正常；继续检查调用者，定位到统计对象指针的错误重定位。

原厂 APFS 的 DATA 基址为 `0xfffffff007c928c0`，统计对象指针槽位为
`0xfffffff007c93bd8`。旧链接器只跟踪同一 ADRP 的首个低位偏移，在 MOV
复制页寄存器后还会丢失原寄存器的后续用途。DATA 被移动到不同页内偏移后，
一条 `LDR x8, [x27, #0xbd8]` 留下旧偏移，读到了 8 KiB zone 指针。
随后的统计更新写入 `zone + 0x58 + 0xe8`，恰好落在下一个 inode zone
的缓存字段，加上本次分配大小 `0x1000`。

修复涉及 `tools/kernelcache_patcher/Patcher.cpp` 与 `KernelMacho.cpp`：

- 逐控制流路径跟踪页基址的复制、寄存器覆盖、调用及有界跳转表。
- 分开处理确定的页基址和路径合并后不确定的指针；不确定访问禁止改变位移。
- DATA 和 DATA_CONST 保留原页内偏移，避免一个源页在目标中被拆到两个页。
- 回归覆盖不同全局偏移、MOV 后原寄存器继续使用、BL 的临时寄存器覆盖，
  以及同一寄存器在不同路径上分别表示全局页和普通对象的情况。

`handoff-40` 首次确认原生 APFS 完成 System 根卷挂载：

```text
BSD root: disk6s1, major 1, minor 82
apfs_vfsop_mountroot: apfs: mountroot called!
mount-complete volume System, requested by: kernel_task (pid 0)
load_init_program: attempting to load /sbin/launchd
```

设备节点编号会随 LUN 枚举变化，启动选择仍使用 System 卷 UUID。

## 压缩文件支持

首次挂载后，执行 launchd 返回 errno 45。串口明确报告压缩文件 type 4
尚未注册。APFS 的 plist 依赖不包含按需匹配的文件压缩插件，因此仅计算
APFS 依赖闭包不足以执行固件里的压缩文件。

`apfs` collection 显式加入原厂
`com.apple.AppleFSCompression.AppleFSCompressionTypeZlib`。
该插件代码段内的 LZVN 跳转表、LZ4 字节重排表、低位掩码和 Adler32
常量池使用通用规则识别，打包与独立 ISA 校验均保留原字节。signed16
跳转表要求字节索引边界、ADR/LDRSH/ADD/BR 结构和全部 256 个合法 BTI 目标；
其余常量池要求完整符合重排、低位掩码或 Adler32 数学定义。识别规则不依赖
Kext 名称、原始地址或固件版本，并使用无关 bundle 的合成样本做回归。
原始地址、提供映像哈希、常量哈希和跳转目标复核记录位于
`../sdm835/ios18/fscompression-table.json`。

## 启动信任缓存

`handoff-42` 已能读取 launchd 和 dyld，但 AMFI 拒绝它们的原厂 ad-hoc 签名。
启动桥此前没有提供 iBoot 的 `chosen/memory-map/TrustCache`。

`scripts/bridge_trustcache.py` 从准备文件系统时选定的 BuildManifest 身份读取
`StaticTrustCache`，核对清单摘要，再解析 IM4P 内的原始模块；不重新提取大型
OS 镜像。当前静态 v2 模块包含 2,830 条记录，其中包含原厂 launchd 的
CodeDirectory 哈希 `262516eeeee58a7445a36776d905090456b2ef7c`。

`--trust-file` 扫描显式指定的文件/目录，为其中已签名的 arm64 Mach-O 生成
独立的 engineering v1 模块。当前 Bash overlay 生成 8 条记录，包含 Bash、
readline、history、ncurses、form、menu、panel 和 libiosexec。Bash 的 SHA-256
为 `50f1a1259ebdcc25453ef53c750aedb52d58eb5053d247bd51b692eb2a29fe68`，
cdhash 为 `1dc48ce68a0438f02b5b72dcda68fa0a761f1687`。

桥在保留的内核内存内复制模块 offset table，以标准物理地址/长度属性交接，
不保留指向 EFI 源缓冲区的指针。`handoff-43` 确认两个模块均成功加载，
System 挂载完成，原厂 launchd 通过 AMFI 并执行到 `Darwin Ignition Sequence`。
这条日志尚未证明 launchd 服务或交互 Bash 已运行。

## ignition 等待点

`handoff-44` 使用通用 `sysctl-trace=1` 记录查询进入/返回，确认 PID 1
停在四级 MIB 对应的 `security.mac.img4.ignition_blob` 处理函数内。
`handoff-45` 使用原有 `io=0x1f` 匹配日志，确认 AppleImage4 已匹配并开始
启动。原厂 AppleImage4 的 finalize 函数无限等待 `IOAESAccelerator`，随后
才释放用户态 cork；当前集合没有具体 AES provider。这比推测 Preboot 或
Cryptex 已失败更精确：后续初始化当时尚未到达。

新增 `GenericAES` 通过 corecrypto 提供同步软件密钥的 AES-CBC。IOAESAccelerator
类大小、继承关系及 vtable 槽位由 `drivers/abi-22H374/apple-crypto-abi.json` 对
固定提供映像验证。发布服务前通过 descriptor API 执行 NIST CBC 加解密向量
及硬件密钥拒绝测试；不为 Apple UID/GID、密钥别名返回伪造结果。

## 内核关联卷挂载参数

`handoff-53` 暴露空 APFS 挂载参数的语义：APFS 将其解释为根容器挂载，
`container_rootmount` 再次通过 `bdevvp` 打开已挂载的外层容器，触发
`bdevvp failed: open` panic。不能将普通关联卷当成第二个根容器。

`imageboot-parent-role` 和 `imageboot-parent-mountpoint`。

不改变自动挂载 Recovery 的配置、不忽略设备打开错误。独立镜像容器仍使用原有
内核设备路径约定。`handoff-54` 验证关联卷和辅助镜像挂载均返回 0：Preboot 通过角色挂载，
原厂 APFS 将原始、未修改的 SystemOS.dmg 挂载到 `/private/preboot/Cryptexes`。

### XID 5 原生启动与签名页粒度

`handoff-59` 已从 EDK2 Fastboot 发送 EFI，原厂 APFS 选中 XID 5 并挂载 System、
Preboot 和原始 SystemOS 镜像，缓存文件可读。dyld 通过新增默认目录链接找到缓存，

项目的 SDM835 平台补丁在 `osfmk/arm/arm_init.c` 强制软件页大小等于 4 KiB
硬件粒度；这覆盖了上游 arm64 的常规页大小选择。引导器当前仅交接 256 MiB 安全 arena，公共默认策略仍会选择 4 KiB。
新增通用 DEVELOPMENT/DEBUG 启动参数 `vm-pagesize=16384`，显式选择 16 KiB
软件 VM 页；pmap 已有 `PAGE_RATIO == 4` 路径，用四个 4 KiB PTE
描述一个 VM 页。硬件 translation granule 和所有代码签名检查保持原样。
已从平台补丁移除这段机型条件分支；通用参数只接受硬件粒度或 PAGE_MAX_SIZE，
不更改代码签名允许列表与页哈希算法。候选内核待上机验证。无需更新 APFS 增量。
